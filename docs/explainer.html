The client's credential is what it is, not a secret it holds.

client-attestation-sdk builds and verifies OAuth attestation-based client authentication in Go, Java, Python, and TypeScript. A workload proves its platform identity once; every port turns that into the same two artifacts — an attestation JWT and a proof of possession — and the same Java verifier accepts all four.

Go · Java · Python · TypeScript ES256 · RFC 7638 kid PoP + DPoP-combined Interop-verified against a real AS

Architecture

01

Two shapes, one contract. Every request-time flow ends the same way — an attestation plus a fresh proof, sent to the token endpoint — whichever proof-of-possession method produced it.

Standards supported

Grouped by what each one governs, not by where it's implemented.

  • ABCAdraft-ietf-oauth-attestation-based-client-auth — the attestation JWT, PoP JWT, and attest_jwt_client_auth
  • RFC 9449DPoP — the combined proof-of-possession mode
  • RFC 7638JWK Thumbprint — every kid in this SDK

Authorization

  • RFC 9396Rich Authorization Requests — authorization_details

Resource server

  • RFC 6750Bearer Token Usage — extraction and challenge headers
  • RFC 9728Protected Resource Metadata — served at /.well-known/oauth-protected-resource

Test coverage

05

Two layers, deliberately different in scope — cross-language agreement on the low-level builder shapes, and per-language unit coverage of everything the orchestration class decides on its own.

Cross-language

verify-interop.sh builds a credential in every language from one shared vector and runs each through the real Java ClientAttestationVerifier, in both PoP and DPoP modes. verify-validation.sh has every port's validator agree on the same pre-signed token vectors — valid, expired, wrong issuer/audience, missing scope, bad signature.

Per-language

Each suite covers what the shared vectors can't reach: evidence auto-detect precedence, signer and network failures, malformed tokens, and that a fetched challenge actually lands in the token-endpoint PoP JWT's challenge claim or the DPoP proof's nonce claim, in both the one-call flow and the SPIFFE issuance bootstrap.
