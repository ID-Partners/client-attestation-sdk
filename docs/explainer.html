Identity and access for AI agents and applications

Help software prove its identity before it gets access.

AI agents and applications need permission to use company systems. Client Attestation SDK helps them prove which application is making a request. A software development kit (SDK) is code that developers add to an application. Your company sets the rules for what that application can do.

Go · Java · Python · TypeScript Uses the application's platform identity

The problem with shared secrets

01

Applications often identify themselves with a shared secret - a password held by the application and the service that checks it. Anyone who obtains that secret can use it to impersonate the application. Teams must protect these secrets and replace them when needed.

This SDK uses identity evidence from the platform where the application runs. An attester is a trusted service that checks identity evidence and issues a signed statement called a Client Attestation. The application presents that statement with proof that it holds the matching private key. A private key is secret data the application uses to sign its proof. This authentication flow uses no shared client secret.

How it works

02

An access token is a credential that an application presents when it calls a protected service. The Authorization Server is the service that checks token requests and issues access tokens. The SDK handles the steps needed to request one.

  1. The SDK obtains identity evidence from the application's platform.
  2. The attester checks the evidence and issues a Client Attestation linked to the application's key.
  3. The application signs a fresh proof with its private key when it requests an access token.
  4. The application sends the access token to the protected service. That service checks the token against its access rules.

What the SDK does

03

Developers can use it in Go, Java, Python and TypeScript. Some features are available only in Python.

Requests access tokens

Handles identity checks and token requests. Reuses tokens until they need refreshing.

Proves possession of a key

Signs a fresh proof for the Authorization Server to check. Copying the Client Attestation alone does not provide this proof.

Checks incoming access tokens

Checks who issued a token, whether it has expired, which service it is for and which permissions it carries.

Handles requests for human approval

The Python version can handle an approval request through a paired device or a web consent link. Your team supplies the approval application and records the decision.

Compare features by programming language

Proof of possession means proving that the application holds the private key linked to its attestation. DPoP (Demonstrating Proof of Possession) is a standard for signing proofs for individual requests. JWT (JSON Web Token) is a format for carrying claims in a token. A challenge is a value from the server that the application must include in its proof. SPIFFE is a standard for identifying software services.

Your company controls access

04

A verified application identity is one input to an access decision. Your services enforce the permissions your company grants.

Identity

The Client Attestation identifies the application. It can also name the person or organisation responsible for running it. Naming that operator does not grant permission.

Permissions

An application can request specific permissions. The service issuing the token decides which permissions to grant. The protected service checks whether they allow the requested action.

Key protection

The application still needs a private key. The SDK supports signing Client Attestations with a key held in OpenBao or HashiCorp Vault.

Human approval

Your access rules decide when a person must approve an action. The Python version includes a check that developers can use to confirm a retried request matches the approved instruction.

What the checks cover

05

The repository includes checks for compatibility between languages and for errors within each version.

Compatibility

Shared examples check that credentials made in each language are accepted by the same Java verifier. Other examples check that all four versions agree when accepting or rejecting access tokens.

Error handling

Each language has tests for failures such as invalid tokens and network errors. These tests also cover how the SDK uses identity evidence and responds to requests for a fresh proof.

These checks cover the SDK and shared examples. Your team needs to test its own identity service, access rules and application together.

Uses OAuth standards

06

OAuth is a set of standards for granting applications access to protected services. This SDK implements revision 10 of the OAuth attestation-based client authentication draft. The specification is still a draft.

The default integration uses PingFederate. Connecting to another identity service requires configuration or integration code. The developer documentation lists the standards and supported features.

What your team needs

07

Your developers add the SDK to the application and connect it to your identity and access services.

  • A supported source of application identity evidence from the platform where it runs.
  • An attester that issues Client Attestations and an Authorization Server that accepts them.
  • Access rules for the systems and actions the application can use.
  • A way to protect the private keys used by the application and the attestation issuer.

Your identity and security team can confirm whether your existing services support this flow. Developers can find installation instructions in the repository README.

Client Attestation SDK provides application code in four languages. The Java verifier used for compatibility checks is in the separate client-attestation project.
